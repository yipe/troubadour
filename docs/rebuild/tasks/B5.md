# B5 · Python type checking with a baseline

**Deps:** B3, W1 · **Size:** S · **Owns:** `backend/pyproject.toml`, `backend/.basedpyright/`, root `package.json`

## Read first
- `docs/rebuild/conventions.md` §1.
- basedpyright docs: configuration in `pyproject.toml`, and baselines (`--writebaseline`).

## Goal
New Python code is type-checked from now on, without first fixing every old error. basedpyright (B1 already
installed it in the `dev` group) records today's errors in a committed baseline file. A new error fails;
fixing an old one shrinks the baseline.

## Steps
1. `[tool.basedpyright]` in `backend/pyproject.toml`: `include = ["packages", "tests"]`,
   `typeCheckingMode = "standard"`, `pythonVersion = "3.12"`, `reportMissingTypeStubs = false`. Exclude
   `spike`. Don't use `all`/`strict`: too noisy for a codebase without annotations.
2. `uv run basedpyright --writebaseline`, which writes `backend/.basedpyright/baseline.json`. Commit it.
3. Root `package.json`: add `"typecheck:backend": "cd backend && uv run basedpyright"` and make `typecheck`
   run both (`yarn typecheck:backend && cd web && pnpm typecheck`).
4. Write `backend/.basedpyright/README.md`: when your change fixes baselined errors, run
   `uv run basedpyright --writebaseline` and commit the smaller file. Never regenerate the baseline to hide
   new errors.

## Edge cases
- Errors that come from third-party packages without stubs (mlx, pyannote) are baselined, not silenced
  globally.
- The baseline is keyed by file path. That's why this runs after B2 and B3 move the code.

## Acceptance
- `cd backend && uv run basedpyright` exits 0.
- Add `x: int = "a"` to any module: it fails. Remove it.
- `yarn check` passes.
