## Shapes (`@troubadour/api/review/types.ts`)
```ts
interface ReviewItem {
  id: string                       // stable: kind + key
  kind: "fact" | "spelling" | "entry"
  line_id: string | null; t: number | null
  status: "open" | "accepted" | "rejected"
  preaccepted: boolean             // kept in the live notebook
  fact?: FactSuggestion & { about: string | null }
  spelling?: { heard: string; entity: string | null; count: number }   // entity null = unknown word
  entry?: { name: string; type: EntityType; description: string }
}
interface Review { session_id: string; written_up: boolean; items: ReviewItem[]; counts: { total: number; done: number; fact: number; spelling: number; entry: number } }
```

## Backend (`lore/review.py` + `routers/review.py`)
1. **Building items** for session `id`:
   - facts: every suggested fact (entities and campaign) whose `source.session_id == id`;
   - spellings: campaign spelling suggestions (`misheard` and `unknown`) whose `heard` word occurs in this session's transcript; anchor at the first such line;
   - entries: suggested entities first mentioned in this session (the earliest mention across saved sessions, using the existing mention scan); anchor at the first line naming them;
   - `line_id` and `t`: from the source time (the line whose span contains `t`, else the nearest start), or the anchor line;
   - `preaccepted`: a kept notebook item for this session matches (`same_fact` for facts, name for entries, heard for spellings). A kept notebook fact with no matching suggestion becomes its own fact item (`about` from the notebook).
2. **Frozen list.** The first GET writes `sessions/<id>/review.json` `{items: [{id, kind, key, line_id, t}], decisions: {}}`. Later GETs add newly appearing suggestions (a re-run write-up) and keep the rest, so `total` stays stable. Statuses come from `decisions`, falling back to the live state (a suggestion that disappeared without a decision counts as `rejected`).
3. `POST /api/sessions/{id}/review/{item_id} {action: "accept"|"reject", text?, about?}`:
   - fact: accept (with an optional edited `text` or a moved `about`) or reject, through the same vault calls as the review endpoint C6 changed. An update suggestion keeps history.
   - spelling: accept → add `heard` to the entity's `heard_as` (misheard) / reject → `reject_misheard`; for an unknown word, accept → create an entry named with the `text` given (the client asks), reject → ignore the word.
   - entry: accept → mark confirmed; reject → delete the suggested note (to `.trash/`, as deletes do).
   - Records the decision in `review.json`, calls `memory.changed()` when the vault changed, and returns the updated item. A second action on a decided item → 409.
4. Serialize review writes per session with a lock (the client queues as well, but don't rely on it).

## Web (`@troubadour/api/review`)
`useReview(id)`, `useReviewAction(id)` built on `useCampaignWrite` (serial; updates the review cache with the returned item and invalidates the campaign).

## Contract rule
Every endpoint you add or change declares a pydantic `response_model` (payload shapes as classes in the router, or in `server/models.py` when two routers share one). In `@troubadour/api`, its types are `Schemas["<Model>"]` from `../generated` (the B6 recipe), not hand copies. WebSocket payloads reuse the same models. Run `pnpm -C web/packages/api gen` after changing a model.

## Tests (`test_review.py`)
Items for each kind with correct anchors; preaccepted from the notebook; the frozen total survives a reject; accept fact → in facts with source; accept update → history; spelling accept/reject paths; entry accept/reject; 409 on a repeat; a session that isn't written up → `written_up: false` and only notebook items.
