## Goal
Classes are a list the app loads. The 12 SRD classes are built in. Users add their own in the app (an artificer,
a homebrew class) with a colour. A player has a class; the class gives the colour unless the player has a
custom colour.

## Backend
1. `core/classes.py`:
   - `BUILTIN = ("barbarian", "bard", "cleric", "druid", "fighter", "monk", "paladin", "ranger", "rogue", "sorcerer", "warlock", "wizard")` with labels (capitalised). These match `@yipe/tokens` `CLASS_NAMES`; a test checks that against `web/packages/tokens/src/classes.ts` (read it as text).
   - `custom_path() = config.DATA_DIR / "classes.json"`, shape `{"classes": [{"id", "label", "color"}]}`. It is resolved per call, so tests redirect it.
   - `all_classes() -> list[dict]` (built-ins with `color: None, builtin: True`, then custom ones), `add(label, color) -> dict`, `update(id, label?, color?)`, `remove(id)`.
   - Rules: `label` 1–40 chars after strip; `id` = a slug of the label (lowercase a–z0–9 and `-`), unique, and never a built-in id (ValueError); `color` must match `^#[0-9a-fA-F]{6}$`; at most 50 custom classes. Built-ins can't be updated or removed (ValueError). A broken file reads as no custom classes (log a warning; don't crash). Writes use `fsutil.write_atomic`.
2. `Player` gains `dnd_class: str | None = None`. `color` becomes `str | None`: `None` means "use the class colour". `add_player` no longer assigns a palette colour (new players get `None`). `migrate_state` keeps every existing player's colour exactly as it is: those were either picked or auto-assigned, and either way the user has seen them. Bump `STATE_VERSION` only if `migrate_state` needs it to stay idempotent. Test the migration on a v2 state dict.
3. `update_player` accepts `dnd_class` (a known class id or `None`; an unknown id is a ValueError → 400) and `color` (a hex or `None`).
4. `core/transcript.build`: record `players[]` carry `dnd_class` and `color`.
5. `routers/players.py`: `GET /api/classes`, `POST /api/classes {label, color}` (201 → the class), `PATCH /api/classes/{id} {label?, color?}`, `DELETE /api/classes/{id}` (204). No WebSocket event: the client refetches `GET /api/classes` after its own writes. Deleting a class that players use is allowed. Those players keep the id and fall back to the next colour rule; the UI shows "unknown class".
6. Pydantic models with the caps above. `PlayerPatch` gains the two fields.
7. `spike/seed/players.py`: classes for the demo players (Pip bard, Thessaly druid, Brann barbarian, Velis wizard, GM none) and one **made-up** custom class, "Tinkerer" (`#8c6040`), unused. Never commit non-SRD class names in code, tests or seed.

## Web (`@troubadour/api/players`)
`DndClass` type; `Player.dnd_class`, `Player.color: string | null`; `RecordPlayer` too. Endpoints `classes()`, `addClass()`, `updateClass()`, `deleteClass()`. Queries: `useClasses()` (key `keys.classes()`), and mutations that invalidate it.

## Contract rule
Every endpoint you add or change declares a pydantic `response_model` (payload shapes as classes in the router, or in `server/models.py` when two routers share one). In `@troubadour/api`, its types are `Schemas["<Model>"]` from `../generated` (the B6 recipe), not hand copies. WebSocket payloads reuse the same models. Run `pnpm -C web/packages/api gen` after changing a model.

## Tests (`backend/tests/test_player_class.py`)
- Built-ins listed first, in order; a custom class round-trips through the file; a broken file → only built-ins.
- Validation: empty, too long, bad colour, a duplicate id, a built-in id, the 51st class, updating or removing a built-in → 400 at the API.
- PATCH a player's `dnd_class` to a custom id works; an unknown id → 400; `color: null` clears the override.
- Migration keeps existing colours; a new player has `color: null`.
- The records of a saved session carry `dnd_class`.
- Built-ins match `web/packages/tokens/src/classes.ts`.
